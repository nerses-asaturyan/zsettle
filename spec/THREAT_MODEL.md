# Threat model

| Threat | Outcome | Mitigation |
|---|---|---|
| Seller sells the item elsewhere after signing | Trade tx invalid (duplicate nullifier); buyer's ZEC untouched | consensus |
| Buyer withholds broadcast after seller signs | Seller's signature is a free option until expiry | expiry bounded by `max_expiry_delta` (default 40 blocks, the ecosystem default); the seller may cancel earlier with `cancel`, which spends the item note to a fresh address of its own account together with one payout note (an item note alone is below the fee)|
| Buyer submits a transaction with no expiry, or one already expired | Perpetual option, or a signature on a dead transaction | policy refuses expiry 0 and expiry at or below the tip |
| Buyer alters the payment after seller signs | Impossible: ZIP 244 sighash commits every action's cv, nullifier, rk, cmx and ciphertext | protocol |
| Buyer forges an envelope without owning any note | Seller signs for nothing; items could be tied up | the anchor must be one of the seller wallet's own recent tree roots and the proof is verified against it, so a proof over a synthetic tree is refused; no offer locks an item in any case |
| Unredacted PCZT sent to seller | Seller learns buyer's full viewing key, witnesses and values | prove, then redact; the seller copy carries no buyer key material and no value trapdoors |
| Seller solves the buyer's values from the value commitments | Seller learns the paying note's value and the change | `rcv` is removed from the seller copy; `cv_net` alone is hiding |
| Seller asked to sign an extra spend | Theft of other seller notes | the service signs exactly one action, the listed item's, so no other note of the wallet can be spent by it; the policy also refuses a trade that spends another note of the listed item account, judged against that account's unspent notes, which the published key derives |
| Many buyers (or one buyer repeatedly) send trades for one item | Several signatures outstanding | all acceptable offers are signed; only one can confirm, the seller is paid once, nothing is locked |
| Tampered listings file | Buyer pays the wrong party or buys the wrong note | the file is signed by the item account's spend key and verified against the published viewing key; unsigned or altered files are refused. The signature proves the file was written by whoever controls these items, not that it is the seller you meant: compare the key fingerprint `list` prints with one the seller gave you out of band |
| Stale listings file served again | Buyer pays yesterday's higher price | the signed body carries the height it was issued at; `buy` warns when it is more than 1,000 blocks old |
| Price paid as dust | Seller receives notes it can never spend at a profit | outputs at or below the ZIP 317 marginal fee do not count as payment |
| Seller's own listings file edited on disk | The service would re-sign and enforce the edit | the service and `publish` refuse a file whose signature does not verify; `publish --resign-unverified` is the one explicit way to sign an edited file, and it still checks every entry (price floor, expiry limit, note ownership) |
| Listings holder reads the buyer's new item note | Buyer's address, value and memo exposed on chain | the item output's outgoing key is the buyer's; the published consignment decrypts no trade output |
| Address reuse links purchases or links the market to a wallet | Buyer's or seller's purchases correlated | every item is received at a fresh diversified address; the payout address is derived for the market, never the default address |
| Published key reveals more accounts | Sapling notes and transparent addresses of the item account exposed | the listing carries the Orchard component only |
| Seller signs against a stale chain view | Expiry check and nullifier set out of date | the service syncs before every pass and refuses to run a pass whose sync failed |
| Wallet directory copied or stolen | Funds and items taken | the mnemonic is age-encrypted, to an identity file created with owner-only permissions (keep it apart from backups) or to a passphrase (scrypt); the database holds viewing keys and notes, so a thief learns the wallet's history but cannot spend |
| Service crash or restart mid-trade | Duplicate signature, lost envelope, torn listings file | replies are named by envelope content, outputs and listings are written atomically, the envelope is moved last, and an envelope whose reply already exists is filed without re-signing |
| Offer flood or malformed requests over HTTP | Disk filled, service stalled or crashed | the endpoint is the service's own: 8 KiB request head, ten-second timeouts, bodies refused above 1 MiB before they are read, 32 connections at once, 503 once 1,000 offers wait; refused envelopes are deleted and only their reasons kept, at most 10,000; envelopes are judged in arrival order, a deferral is given up after ten blocks, and at most 100 envelopes stay deferred per pass, so a flood of unprovable envelopes holds the service's attention for minutes, not for the expiry window |
| Proof-verification flood by a listings holder (who can prove a spend of a listed note against a synthetic tree) | Service CPU | the public checks run first (at most three actions, branch, expiry, anchor known, the listed item spent once with a randomizer); the proof second, once per envelope; a deferred envelope is not verified again |
| Service used as an oracle: envelopes built to learn from the refusal whether an address, a note or another consignment is this wallet's | Seller's addresses, payout history, other notes | the policy decides on public data only: an output counts as payment only to the listed payout address, and the extra-spend check uses the listed account's own notes, which the published key derives; the public checks run before the proof and the payment check after it, so no refusal, before or after a valid proof, depends on anything a listings holder could not compute. Tested: a sibling address of the payout account is refused in the same words as a stranger's |
| Shared inbox readable by other buyers | Buyers see each other's envelopes, nullifiers and refusals | with `--listen` each buyer posts its own envelope over HTTP and can fetch only the reply to its own content tag; the directory transport is for parties on one machine |
| Hostile inbox (huge files, unreadable files, name collisions) | Memory exhaustion, stalled service, dropped envelopes | envelopes above 1 MB are refused unread; one bad envelope is quarantined without failing the pass; replies are named by content tag |
| Light server down or flaky | Service stops | failed passes are logged and retried with exponential backoff up to five minutes; nothing is signed in a failed pass |
| Reorg or incomplete sync hides an item note | Item wrongly delisted | an item is removed only when the wallet has recorded a spend of its note; a spend seen only in a compact block counts for 40 blocks after it was first observed, as in the wallet library, so a spend undone by a reorg does not hide the note for good |
| Network upgrade this build does not know | Transactions silently rejected | the tools compare the server's consensus branch with their own before building or sending and stop with a message |
| On-chain fingerprinting of trades | Trades identifiable without keys | standard expiry delta, standard ZIP 317 fees, standard anchor depth, two or three actions like any wallet transaction; a non-default `--min-confirmations` changes the anchor depth and would make a trade stand out, so the default is kept |
| Window-shoppers hold the item FVK | They learn when and that the item sold or was cancelled (a cancel sends it to a fresh address of the same account), and see every other item of that account | inherent to consignment; limit it to one item per consignment with `new-item-account` |
| Fee or change manipulation | Seller underpaid | policy decrypts the payment outputs under the seller's incoming viewing key and checks `>= price` |
| Envelope for another consensus branch | Signature on a transaction the chain cannot accept | policy compares the envelope's branch id with the one live at the next block |

## What stays visible
- The listed price and payout address, by the seller's choice.
- To anyone holding a consignment: the item notes of that account, their values and names, and the block in which each one was spent.
- To the light server: the IP behind every call; the block ranges a wallet scans, from its birthday; on `import-listing`, the tree state at the listing's birthday, which identifies the public listing imported; on `verify` without `--private`, the item's genesis transaction, which names the item (with `--private` only the listing's birthday, which still names the consignment); the full transaction on broadcast. zsettle is Orchard-only and makes no transparent-address query; the one transparent-UTXO refresh the library performs each sync is answered inside the process (`broadcast::Shielded`, matching the method path under any server path prefix), so no transparent address reaches the server as long as the pinned libraries make no other transparent query. Route through Tor or run your own lightwalletd if the rest matters.
- To the seller, when offers go over HTTP: the buyer's IP, unless the buyer comes through Tor (`HTTPS_PROXY=socks5://127.0.0.1:9050`, or `ALL_PROXY`, is honoured by the HTTP transport of `buy` and `finish`; the lightwalletd connection is not proxied, so run your own lightwalletd or the whole command under a transparent proxy). The envelope also carries the item account's full viewing key in the clear on the item action (the signer needs it), so an observer of the envelope holds the consignment even without the listings file. The service never answers anything but the reply to a given content tag. Fetching the listings by URL (`list`, `import-listing`, `buy` or `verify` with `--listings http://…`) shows the service the same: the IP, the time and the client's `User-Agent`, nothing from the wallet; a window-shopper is visible to the seller as such. A proxy variable the transport cannot use stops the command instead of being skipped.
- To anyone sending offers: the seller's sync state, chain-class information: whether an offer waits (its anchor or expiry is ahead of the seller's scan) and whether the wallet is behind on a listed note; refusal texts name no height of the seller's own.
- To holders of the listings file: the height the file was last signed at (`issued_at`), which the service refreshes after every sale, so the seller's sync height at that moment; and the item account's birthday, rounded down to a thousand blocks, which is also the height the seller's wallet asked the light server a tree state for when it made the account.
- To the light server, from the seller: a sync every five seconds while the service runs, which marks the IP as a running service. `verify` reads its block stream to the tip even after the trace resolved, so the server does not learn where the item last moved.
- To the seller: the nullifier of the buyer's paying note, from the envelope. If the offer settles, the chain reveals it anyway. If the offer does not settle (lost race, expiry, abandoned), the seller could later recognise the transaction in which that note is finally spent; `zsettle rotate` retires such notes in a plain two-action transfer to the buyer's own account, after which the nullifier points at that transfer and nothing else. With an exact-value two-action offer the seller, and anyone holding the listings file who recognises the trade on chain, learns that note's value (price plus fee).
- Nothing else links the buyer's paying note, the buyer's address, the seller's other notes or either party's balance to the trade.
